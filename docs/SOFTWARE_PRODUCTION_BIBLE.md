## 1. Product Vision, Boundaries & Success Criteria

```text
The platform is a visual consultation and patient-engagement system for aesthetic medicine practices. It
unifies patient records, standardized clinical photography, consultation workflows, education, treatment
planning, consents, before/after comparison, secure communication, telehealth, and clinician-controlled
AI aesthetic visualizations.
```

### 1.1 Product goals

```text
• Give providers one consultation workspace from intake through follow-up.
• Standardize clinical photography so before/after comparisons are more consistent and reproducible.
• Provide clinician-controlled visual simulations without representing them as guaranteed outcomes.
• Keep patients engaged through a dedicated patient application containing only released materials.
• Create traceable, versioned consent and media-permission workflows.
• Support future EMR connectivity without coupling the product to one vendor.
• Create a commercial SaaS architecture that can grow from a small pilot to thousands of practices.
```

### 1.2 Explicit non-goals for initial production

```text
• The AI system will not automatically diagnose conditions.
• It will not independently prescribe medication, product, dosage, injection depth, or surgical
technique.
• It will not present a visualization as an exact prediction or guaranteed result.
• The MVP will not attempt to replace a full billing, claims, e-prescribing, or enterprise EHR system.
• Cross-practice patient data sharing is prohibited unless a later approved feature defines authorization
and consent.
• 3D digital-patient modeling is deferred unless separately authorized.
```

## 9. AI Aesthetic Outcome Simulation

```text
Product language: simulation or visualization, not guaranteed result, exact prediction, or
outcome probability.
```

### 9.1 Patient-facing disclaimer

```text
AI-generated visualization for consultation purposes. Actual clinical outcomes vary. This visualization is
not a guarantee or prediction of medical results.
```

### 9.2 Simulation pipeline

```text
Source image(s)
-> Input quality validation
-> Landmark detection
-> Treatment-region segmentation
-> Identity representation
-> Provider-defined visualization parameters
-> Constrained transformation
-> Outside-region identity similarity check
-> Artifact detection
-> Output validation
-> READY_FOR_PROVIDER_REVIEW
-> Provider approve / reject / regenerate
-> Explicit release to patient
```

### 9.3 State machine

```text
DRAFT
-> QUEUED
-> PROCESSING
-> VALIDATING
-> READY_FOR_PROVIDER_REVIEW
-> APPROVED | REJECTED | REGENERATING | FAILED
APPROVED -> RELEASED_TO_PATIENT
Any retained terminal result -> ARCHIVED when allowed
```

### 9.4 Provenance

```text
• source asset IDs
• procedure/treatment region
• AI model ID and version
• inference configuration and provider-set parameters
• mask/segmentation reference when retained
• output asset ID
• timestamps
• generating user
• reviewing provider
• approval and release events
```

### 9.5 Identity-preservation rules

```text
The system must minimize unintended changes outside the treatment region. A lip visualization must not
unnecessarily alter eyes, nose, ears, hair, unrelated skin, background, or overall identity. Outputs
crossing configured artifact/similarity thresholds are rejected or flagged before release.
```

### 9.6 Initial visualization categories

```text
Category Provider controls / restrictions
Lip filler Upper/lower visual volume, projection, Cupid's bow/vermillion
definition; no dosage
Rhinoplasty Bridge/dorsal contour, tip projection/rotation, width; no
surgical-technique recommendation
Botulinum-toxin aesthetic visualization Region-based appearance visualization; no brand, drug, units,
depth, needle, or injection plan
Cheek/chin/jaw filler Visual contour/intensity only; no product or dosing
Facelift/neck lift/blepharoplasty/brow lift Visualization parameters defined per validated model; no
guarantee
Breast/body contour procedures Multi-view visualization when validated; no operative-plan
automation
Skin resurfacing/tightening Appearance visualization only within validated domain
```

### 9.7 Model registry

```text
Every production model has immutable model/version records, validation metadata, activation status,
and rollback capability. A production model is never silently replaced.
```

## 21. Authentication, Security & Privacy Architecture

### 21.1 Authentication

```text
• OIDC/OAuth-compatible identity architecture.
• Short-lived access tokens and controlled refresh/session lifecycle.
• Server-side session/device revocation.
• Provider-app Face ID / Touch ID reauthentication using LocalAuthentication where appropriate.
• Secrets stored in Keychain on iOS.
• Administrative MFA support/requirement according to deployment policy.
```

### 21.2 Security rules

```text
• TLS in transit.
• Encryption at rest for database, object storage, backups, and applicable local cache.
• KMS-managed keys/envelope encryption where appropriate.
• No sensitive data in application logs, analytics, crash payloads, or push notifications.
• No public object buckets or permanent public patient-media URLs.
• Tenant isolation enforced in application/service layer and tested automatically.
• Signed temporary media access.
• WAF/rate limits/abuse monitoring for public endpoints.
• Secrets Manager or equivalent for backend secrets.
• Least-privilege IAM and service-to-service authentication.
• Immutable/tamper-resistant audit strategy appropriate to deployment.
• Dependency and container vulnerability scanning in CI.
```

### 21.3 HIPAA-ready posture

```text
The technical design should support healthcare privacy/security obligations when deployed for covered
workflows, but legal compliance depends on the customer's role, contracts/BAAs, policies, training,
incident response, retention, and configured services. The software specification therefore requires
compliance-ready controls without claiming that code alone makes an organization compliant.
```

### 21.4 AI/regulatory boundary

```text
Patient-specific aesthetic visualizations and any future clinical decision-support features require
intended-use and regulatory review before claims expand. Initial AI is clinician-controlled visualization
with provider review and no automatic dosing, diagnosis, treatment recommendation, or guaranteed-
outcome language.
```


### 22.2 Audit event contents

```text
Actor, organization, resource type, resource ID, action, timestamp, request/correlation ID, and
appropriate device/session metadata. Avoid embedding clinical content itself in audit metadata.
```

### 22.3 Retention

```text
Retention periods must be policy-driven and configurable by deployment/customer requirements.
Deletion/archive workflows must respect legal/clinical retention obligations, backups, and downstream
integrations. Claude must not hard-code one universal retention period.
```

### 22.4 Patient export

```text

and download are audited. Large exports use asynchronous server jobs but the UI must expose job status;
no hidden background work.
```

## 23. Offline Mode, Local Storage & Synchronization

### 23.1 Allowed offline

```text
• View explicitly cached recent patients according to policy
• Capture new clinical photographs
• Draft notes/consultation content
• Annotate locally cached photos
• Queue uploads/mutations
```

### 23.2 Not available offline

```text
• Server AI generation
• EMR sync
• Operations requiring real-time authorization confirmation
• Finalization steps configured as server-dependent
```

### 23.3 Sync rules

```text
• All cached sensitive data encrypted.
• Queue operations with deterministic IDs/idempotency.
• Retry safely without duplicate signatures, records, or AI jobs.
• Detect edit conflicts and surface them explicitly.
• Do not silently choose the newest timestamp when doing so may discard clinical/consent information.
• Local media is purged according to cache policy after successful secure upload and verification.
```
